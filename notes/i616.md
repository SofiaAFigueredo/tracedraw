# #616 "TraceDraw slow to a crawl": diagnosis

Report: an older Windows 10 Pro 22H2 office PC (ESU updates). TraceDraw 0.16.0
uses about 100 % CPU nearly all the time and cannot be used. Turning hardware
acceleration off does not help. `tracedraw.exe --renderer=gl` does not start
at all. The reference program (its 2019 version) runs well on the same PC.

Code read at HEAD `50ef60c` (Release 0.17.0). Between 0.16.0 (`fa09452`) and
HEAD, the startup and renderer code changed in only three ways, and the
reasoning below holds for both versions:

- `gpu.rs:190`: `SurfaceConfig::LOW_LATENCY`, which queues one frame instead of two (#655).
- The drawn cross hair and I-beam (`ui/cursors.rs`, #655).
- The single-window hand-over (`instance.rs`, `main.rs:176-185`, #646).

The locked dependencies are the same in both: eframe/egui/egui-wgpu/egui_glow
0.36.2, wgpu/wgpu-core/wgpu-hal 30.0.1, glutin 0.32.3 and winit 0.30.13.

| Intel Haswell/Broadwell HD 4x00/5x00/6000, NVIDIA Fermi | feature level 11_x but resource binding tier 1: **rejected** by wgpu-hal | usually none on Windows | GL 4.x, accepted | should open | Hardware through wgpu's OpenGL path |
| Intel Ivy Bridge HD 2500/4000, AMD HD 5000/6000 (TeraScale) | none | none | GL 4.x, accepted | should open | Hardware through wgpu's OpenGL path |

Why each GPU lands there:

- wgpu-hal drops a D3D12 adapter in these cases:
  - it cannot create a feature level 11_0 device (`dx12/adapter.rs:93`);
  - its resource binding tier is 1 (`dx12/adapter.rs:243-253`, "We require Tier 2 or higher");
  - it lacks shader model 6 while DXC is in use (`dx12/adapter.rs:410-422`).
  Only "Microsoft Basic Render Driver" (WARP, `DeviceType::Cpu`,
  `dx12/adapter.rs:171,197`) always passes these checks.
- wgpu's OpenGL path rejects anything below GL 3.3 (`gles/adapter.rs:265-272`).
- egui_glow needs GL 2.0+ (`egui_glow painter.rs:163-164`).

Both symptoms together, a pegged CPU in either mode plus a GL start that dies,
point to the first two rows: **the window is drawn by WARP, the D3D12 software
rasterizer, and there is no usable OpenGL 2.0+ driver.**

## 2. What the log shows: to fill in (the lines that decide it)

`tracedraw.log` is in `%APPDATA%\TraceDraw\` (or a portable copy's
`tracedraw-settings`). Each start rewrites it, except a start with
`--renderer=`, which appends to it (`startup_log.rs:48-58`). The filter is
`info` unless `RUST_LOG` is set (`startup_log.rs:59`).

Lines to look for:

- `TraceDraw 0.16.0 on windows x86_64`: one per start (`startup_log.rs:62-67`).
- `Software rasterizer detected - loss of performance expected. backend: Dx12, device_type: Cpu, name: "Microsoft Basic Render Driver" ...` (egui-wgpu `lib.rs:461`):
  - present: **WARP draws the window.** Expect this line in both the hardware
    and the software start.
  - absent: a hardware adapter was used. Its name is logged only at debug, so
    it is not in the file.
- `Returned GL context is X.Y, when 3.3+ is needed` (wgpu-hal `gles/adapter.rs:268`): wgpu's OpenGL path refused the driver. This gives its GL version.
- `Missing downlevel flags ...` (wgpu-core `instance.rs:924`): a limited adapter.
- `WGL_EXT_swap_control is unsupported` or `unable to set swap interval` (wgpu-hal `gles/wgl.rs:835,851`): no vsync on wgpu's OpenGL path, so frames are not paced.
- `Dropped frame with error: Timeout` (egui-wgpu `lib.rs:410`): WARP could not deliver a swap-chain image in time.
- Lines from the `--renderer=gl` start, which are appended:
  - `Exiting because of error: egui_glow: egui_glow requires opengl 2.0+.` (eframe `run.rs:162`): GDI Generic OpenGL 1.1, meaning no vendor OpenGL driver.
  - `Exiting because of error: Found no glutin configs matching the template ...` or `... glutin error: ...`: no usable pixel format or context.
  - `Failed to create context using default context attributes ...` (eframe `glow_integration.rs:1156`): the core context failed and GLES is retried.
  - `failed to find a matching configuration for creating glutin config`: a **panic** inside eframe (`glow_integration.rs:1110-1113`). It also leaves `crash.log` and should show a message box.
  - Nothing after the version line: the start died before the event loop (or, in 0.17, it handed over to a running window, see RC4).
- `the window did not open with Hardware (...); trying the next renderer` (`main.rs:279`): appears only when wgpu could not open the window at all. It is not expected here, because WARP always opens it.

Timings: none. Neither 0.16.0 nor 0.17.0 logs frame times, frame counts, page
render times or startup duration, so the log cannot show how slow it is.

## 3. Root causes

### RC1. WARP is accepted silently in both modes, so the switch cannot help

- `gpu.rs:176-183`, the adapter selector:
  - Software mode takes the CPU adapter (`gpu.rs:179`).
  - Hardware mode takes the named card, else any non-CPU adapter, else
    **`.or_else(|| pick(&software))` (`gpu.rs:182`): WARP again.**
  - When wgpu accepts no hardware adapter (section 1), "Use hardware
    acceleration" on and off both draw with "Microsoft Basic Render Driver".
    This matches "disabling hardware acceleration does not help".
- `main.rs:275-283` and `gpu.rs:68-74`: the fallback chain Hardware, then
  Software, then GL runs only when `run_native` fails. WARP never fails to open
  the window, so the chain never goes past it. The chain also puts Software
  (WARP) before GL, so GL is never tried automatically while WARP "works".
- `gpu.rs:116-120`: Options lists adapters for `Backends::PRIMARY` only. The
  start uses `PRIMARY | GL`, the egui-wgpu default from `WgpuSetupCreateNew::without_display_handle()`
  (`gpu.rs:163`, egui-wgpu `setup.rs:245-246`). So wgpu's OpenGL adapter
  can draw the window but never appears in the list.
- The user is never told. Options > General shows "in use: Microsoft Basic
  Render Driver (Dx12)" (`gpu.rs:98-105`, `ui/options.rs:678-680`), but only if
  they open it, and with no hint that it means "slow".

### RC2. A software adapter draws every frame on the CPU, and nothing paces frames or lightens drawing for it

- egui redraws the whole window on every frame, and every input event is a
  frame: each mouse move over the window, each hover change.
- With WARP, D3D12 rasterizes all of it on the CPU, multi-threaded, so it
  occupies every core:
  - the panels, the toolbars, the dockers and their text;
  - large translucent meshes such as window and popup shadows and the AA
    feathering fringes;
  - the full-canvas page texture.
- Vsync is on (`AutoVsync` in egui-wgpu `lib.rs:87-101`; `gpu.rs:190` keeps
  it), so frames are capped at the monitor rate. On an older CPU a WARP frame
  of a maximized 1080p window costs tens of milliseconds, so the cap is never
  reached. Moving the mouse alone keeps every core busy and input queues up:
  "crawls to a halt, 100 % CPU nearly all the time".
- Nothing in TraceDraw reacts to a CPU adapter (`gpu.rs:86-106`,
  `main.rs:249-255`). There is no frame-rate limit, no cheaper visuals (shadows
  and feathering stay on), and the drawn pointers stay on.
- In 0.17 the cross hair and I-beam are painted by the app (#655), so on WARP
  the pointer itself trails by a slow frame.
- In 0.17, `LOW_LATENCY` (frame latency 1, `gpu.rs:190`) stops the CPU from
  building frame N+1 while WARP still rasterizes frame N. On a software adapter
  that means lower throughput, though not more CPU time.
- High DPI: nothing in TraceDraw enlarges the surface. It is the window's size
  in physical pixels (`Current Mode` in dxdiag), so it only matters if dxdiag
  shows a large or scaled mode.

### RC3. The CPU-side work in each frame is small but does run every frame

- `main.rs:411` calls `app.autosave_settings()`, which calls
  `settings_changed()` (`app.rs:3006-3041`) on every frame:
  - `sync_settings()` (`app.rs:2778-2803`) rebuilds the tool, view, panel,
    toolbar and docker preferences;
  - `serde_json::to_string(&self.settings)` (`app.rs:3035`) serializes the
    whole `Settings` struct (118 fields, many `Vec`s);
  - the result is compared with the last string.
  Any one frame costs little, but this runs on every frame and on an old CPU it
  adds to every mouse move.
- The audit for "a repaint loop that never idles" found none that runs without
  input. Each repaint request in the app is conditional:
  - polls at 100 ms only while a GitHub, AI or mosaic job is pending
    (`main.rs:376-395`);
  - the script debugger at 50 ms and the Time Tracker at 1 s, only while
    running (`ui/mod.rs:292-311`);
  - linked-bitmap checks at 1 Hz, only while linked files exist (`clipboard.rs:409-456`);
  - macros at 30 ms, only while running (`ui/macros_ui.rs:68-70`);
  - spinners and the update check, only while busy;
  - the page re-render after a 0.12 s settle (`raster.rs:17,299-307`);
  - the splash at 16 ms, only while shown (`splash.rs:115`);
  - overflow bars, clones and the navigator pan, which converge
    (`ui/overflow.rs:185,285`, `ui/mod.rs:629-633,897-902`);
  - settings autosave, waiting at most 1 s (`app.rs:3027`).
- One repaint source sits outside TraceDraw. egui-wgpu requests a new frame
  whenever the surface reports `Outdated` or `Lost` (`winit.rs:610-623`), and
  logs those only at trace or debug (`lib.rs:392-402`). A surface stuck in
  that state would loop invisibly. It is not expected on D3D12, but TraceDraw
  cannot see it today (see E4).
- So the measured "100 % all the time" is most likely RC2: frames that cost
  too much, triggered by ordinary input. A hidden loop is less likely, and the
  logging in E lets the next log prove which it is.

### RC4. The GL start fails invisibly

- `main.rs:275-283`: GL is the last renderer, so the error is returned
  (`r => r`) and printed to stderr. The Windows build has no console
  (`main.rs:9`), and TraceDraw neither logs it nor shows a message box. eframe
  logs `Exiting because of error: ...` itself (`run.rs:162`), but only when the
  failure happens inside the event loop. The user sees nothing: "doesn't start
  at all".
- The likely causes, in order:
  1. No OpenGL 2.0+ driver (GDI Generic 1.1): `egui_glow requires opengl 2.0+`.
  2. No pixel format matching eframe's template: the `expect` panic at
     `glow_integration.rs:1110-1113`, which also bypasses the restart chain.
  3. Context creation errors.

  The appended log lines in section 2 decide which.
- 0.17 adds a second trap. A `tracedraw.exe --renderer=gl` started by hand
  while a TraceDraw window is still open hands its files to that window and
  ends (`main.rs:179-182`, `instance.rs:101-108`: `--renderer=` is not
  excluded). This happens before `startup_log::init()` (`main.rs:188`), so
  nothing is logged. A retest on 0.17 must close every TraceDraw window first,
  or pass `--new-instance`.

### RC5. The log has none of what this issue needs

- The chosen adapter is logged only when it is a CPU adapter (egui-wgpu warn).
  A hardware pick is debug-only (egui-wgpu `lib.rs:455-463`).
- `note_renderer` (`gpu.rs:86-106`) works out the adapter name and backend but
  only stores them for Options.
- The adapter list is never logged. TraceDraw's own selector bypasses
  egui-wgpu's `request_adapter`, the only place that logs "There are N
  available wgpu adapters" (egui-wgpu `lib.rs:189-193,238-240`).
- Why wgpu-hal drops an adapter (tier 1, shader model, device creation) is not
  logged at all. wgpu-core's backend and adapter elimination lines are debug-only
  (wgpu-core `instance.rs:134-139,505-531`).
- Missing entirely:
  - the mode and why it was chosen (argument, `working_renderer` or setting);
  - the driver version, surface size, `pixels_per_point`, monitor size, present
    mode and frame latency;
  - the GL vendor, renderer and version on a GL start;
  - frame counts and frame times, page render times, time to first frame;
  - repaint causes;
  - CPU thread count and Windows build.

## 4. Fix plan

### A. Choosing the renderer (`gpu.rs`, `main.rs`, `docs/behavior/about-and-startup.md`)

1. Hardware mode no longer takes a CPU adapter. In the selector
   (`gpu.rs:180-182`), drop the final `.or_else(|| pick(&software))` and
   return an error such as "no graphics card can draw the window (only the
   software adapter)". The start then counts as failed and goes on to the
   next renderer.
2. New order: **Hardware, then GL, then Software** (`Mode::next`,
   `gpu.rs:68-74`). Software stays last because it always opens, so it is the
   safety net. On these machines:
   - with a GL 2.0+ driver, GL is used and is much cheaper than WARP;
   - without one (GDI Generic), GL fails with the egui_glow error and the
     chain lands on Software, which is no worse than today.
   - `working_renderer` already remembers the result, so later starts skip
     the probing.
   - Update the `gpu::tests::a_renderer_that_fails_hands_over_to_the_next`
     expectations and the behaviour doc (section "The renderer").
3. Make the GL attempt survive eframe's glutin `expect` panic. Run
   `run_native` under `std::panic::catch_unwind(AssertUnwindSafe(..))`; the
   release profile unwinds. If a next renderer exists, restart with it. The
   panic hook still writes `crash.log` but skips the message box when the chain
   will continue (a flag set before `run_native`).
4. With hardware acceleration off, Software stays, because it is the user's
   explicit choice. Options shows "(software adapter: slow)" next to it.
5. List the same backends the start uses in Options (`gpu.rs:116-120`:
   `PRIMARY | GL`), and mark CPU adapters "(software)".
6. 0.17: a start with `--renderer=` does not hand over to a running window
   (add it to `instance::hands_over`, `instance.rs:101-108`). Alternatively,
   log the hand-over before ending.

### B. A software adapter is paced and draws less

1. `note_renderer` decides `software: bool` and keeps it in a static next to
   `IN_USE`. It is true for a wgpu `DeviceType::Cpu` adapter, or for a GL
   `GL_RENDERER` containing "GDI Generic", "llvmpipe", "SwiftShader" or "Basic
   Render".
2. Frame-rate limit while software: in `Shell::ui` (`main.rs:334`), keep the
   time of the last frame. If the new frame comes sooner than 1/30 s (a
   constant, maybe 1/20 on very slow machines), sleep the rest before building
   it. Winit queues the pointer moves meanwhile and egui merges them into the
   next `RawInput`, so the frame count drops while the newest pointer position
   still shows. Nothing changes for hardware adapters.
3. Cheaper visuals while software:
   - `ctx.tessellation_options_mut(|o| o.feathering = false)`;
   - window, popup and menu shadows set to `Shadow::NONE` in `theme::visuals()`;
   - the system cross hair and I-beam instead of the drawn ones (`ui/cursors.rs`),
     since a drawn pointer trails by a slow frame.
4. Frame latency: keep `LOW_LATENCY` for hardware. Measure `HIGH_THROUGHPUT`
   (latency 2) on software, where building one frame can overlap WARP
   rasterizing the previous one on another core.
5. Tell the user once, when the window is drawn by a software adapter: a status
   bar note or a dismissible notice. It names the adapter and says that
   installing the graphics card's driver, or OpenGL, would be faster.
6. Check by hand with a software adapter forced locally:
   - commands: `--renderer=software` on Linux, which uses lavapipe/llvmpipe;
     `WGPU_BACKEND=gl` with `LIBGL_ALWAYS_SOFTWARE=1` for the GL software path;
   - compare CPU time and frames per second while moving the pointer over a
     maximized window, before and after.

### C. Idle when nothing changes

1. The audit (RC3) found no repaint that runs forever without input. Keep it
   that way with a test: run an `App` with a document open, dockers open and
   then the welcome screen, through N `egui::Context::run` passes with no
   input after start-up settles. Assert `!ctx.has_requested_repaint()` and
   that no `request_repaint_after` shorter than 1 s is pending.
2. Make the per-frame settings check cheap (`app.rs:3006-3041`). Run
   `settings_changed()` only on frames that had input or a command, or at most
   once a second; the write already waits a second. Alternatively, keep a
   revision counter on `Settings` instead of serializing it to JSON every frame.
3. In the frame statistics (E3), warn when frames keep coming without input,
   and name the repaint causes (`egui::Context::repaint_causes()`, egui
   `context.rs:1947`).

### D. The GL path

1. `main.rs:275-283`: when no renderer is left:
   - `log::error!("the window could not be opened with {mode:?}: {e}")`;
   - show a message box with the reason and the log path (make
     `startup_log::show` `pub(crate)`);
   - return a non-zero exit code.
2. Before `run_native`, log `opening the window with {mode:?} ({reason})`,
   where the reason is the `--renderer=` argument, the remembered
   `working_renderer`, or the setting.
3. On a GL start, `note_renderer` logs `GL_VENDOR`, `GL_RENDERER`,
   `GL_VERSION` and `SHADING_LANGUAGE_VERSION` from `cc.gl` (eframe
   `CreationContext::gl`), and sets `software` for GDI Generic and similar.
4. If the reporter's log says `egui_glow requires opengl 2.0+`, no vendor
   OpenGL driver is installed. TraceDraw cannot fix that in GL, so A2 plus B
   (WARP made bearable) is the answer, together with the advice to install the
   card's driver.

### E. What the log records next time (`startup_log.rs`, `gpu.rs`, `main.rs`)

1. At start:
   - CPU threads (`std::thread::available_parallelism`) and `PROCESSOR_IDENTIFIER`;
   - the Windows build (`CurrentBuild`/`UBR` from the registry, or `RtlGetVersion`);
   - the renderer mode and its reason (D2).
2. In the adapter selector, at info:
   - every adapter wgpu offers: name, backend, device type, vendor:device id,
     driver, driver_info, surface supported;
   - the one picked and why (the named card / the fastest / software);
   - the chosen adapter even when it is hardware, which egui-wgpu logs only at
     debug.
3. Frame statistics: every 10 s while frames happen, so an idle window adds
   nothing. One info line:
   - frames, and how many had input;
   - mean / p95 / max time spent in `Shell::ui`, and between frames;
   - page renders and their mean time (`raster.rs` `last_seconds`);
   - the top `repaint_causes()`;
   - plus time to first frame, once.
4. Surface:
   - format, present mode and frame latency;
   - window size in physical pixels, `pixels_per_point`, monitor size.

   Also pass TraceDraw's own `on_surface_status` in `WgpuConfiguration`
   (`gpu.rs:186-193`). It counts `Outdated`, `Lost`, `Timeout` and `Occluded`,
   logs the first of each kind at info and a count each minute, and keeps
   egui-wgpu's actions (reconfigure, recreate, skip).
5. Make the backend lines that matter visible: default filter
   `info,wgpu_core::instance=debug`, which shows backend creation and why
   adapters were eliminated without flooding the log every frame. Document
   `RUST_LOG` in the about-and-startup doc.

### F. To ask the reporter now (works with 0.16/0.17, no new build)

1. Options > General: what does the "in use" line say?
2. From `cmd`, with every TraceDraw window closed:
   ```
   set RUST_LOG=info,wgpu_core=debug,wgpu_hal=debug,egui_wgpu=debug,eframe=debug,egui_glow=debug
   tracedraw.exe
   ```
   Use it briefly, close it, then run `tracedraw.exe --renderer=gl` (on 0.17
   also add `--new-instance`). The second start appends to the same log.
   Attach `%APPDATA%\TraceDraw\tracedraw.log` (and `crash.log` if there is one).
3. From dxdiag's Display tab: card name, driver version and date, driver model,
   feature levels, current mode.
4. If dxdiag shows "Microsoft Basic Display Adapter", installing the vendor's
   driver (even an older Windows 7/8 one) should make it usable right away,
   and probably GL as well.
